# 迭代简报：user-vibeloop 实战反馈（2026-07-13）

**给本项目智能体**：以下六项来自工作台在 user-vibeloop 项目上的真实使用（4 轮决策会话 + 嵌入真实系统操作，用户 Michael 亲测）。原始记录见 `docs/feedback-log.md` 同日条目。按优先级排列，每项带验收标准。动手前先读 `DESIGN.md`/`PRD.md` 对齐既有架构，遵循本仓库现有代码风格与测试惯例。

## P0 · 修复：embed 代理不转发 POST，嵌入页表单不可用（bug，有实证）

**现象**：把真实系统页（vibeloop 决策队列 `http://localhost:8123/decisions`）作为 embed 块嵌入后，用户在嵌入页内提交裁决表单 → 返回 `{"error":"口令无效…"}`；同一表单、同一口令**直连原页提交则成功**（对照实验已做：用故意非法的选项 id 做探针，直连返回"非法选项"证明鉴权通过，嵌入路径返回 403 证明口令字段丢失）。

**根因线索**：`src/server/server.mjs:219` —— `/api/proxy` 路由条件是 `method === 'GET'`，代理只支持 GET。被代理页面内的相对路径表单 POST 没有任何转发通道。

**要求**：
1. 代理支持 POST/PUT/DELETE：完整透传 method、请求体、`Content-Type`（含 `application/x-www-form-urlencoded` 与 `application/json`），响应也完整回传；
2. 被代理页面内的相对 URL（表单 action、fetch）能正确落回代理通道（现有 GET 的 URL 改写机制延伸到非 GET 即可）；
3. 回归测试：起一个本地 echo 服务，经代理提交表单，断言字段无损到达；
4. 安全边界不放松：代理仍只允许现有白名单/同源策略范围内的目标。

**验收**：在嵌入的 vibeloop 决策页里完成一次真实裁决提交（或等价集成测试）。

## P1 · 新增：会话级常驻"给 AI 留言"入口

**现象**：用户有块级批注之外的话想说时无处可说——实测中用户被迫把一条与 Mac Studio 相关的重要反馈挂在不相干块的批注里，并自己吐槽"是不是缺少一个常驻的让用户给 AI 反馈的入口"。

**要求**：渲染页常驻一个自由输入区（位置建议：提交栏上方或右侧栏固定），内容随 feedback 一并回传，协议建议 `feedback.sessionComment`（string，可空）或保留 items 里 `blockId: "__session__"` 的约定——选一种并同步 `src/protocol/schema.mjs` 与文档。

**验收**：不针对任何块也能留言并出现在 feedback.json；老消费者（不认识新字段）不受影响（向后兼容）。

## P1 · 新增：live embed 的"实时系统"标识

**现象**：嵌入真实运行系统后，用户误以为"这是给我看的样例"，差点错过必须执行的操作。

**要求**：embed（及 prototype iframe）块协议加可选 `live: true`；渲染时给块加显著的"⚡ 实时系统"角标/边框态，与静态示例视觉区分。schema 校验放行未知旧内容（向后兼容）。

**验收**：`live: true` 的块有肉眼可辨标识；无该字段行为不变。

## P1（创始人加权：本轮最高 UX 优先级）· 决策块结构化：上下文 / 原因 / 选项利弊

**现象**（Michael 2026-07-13 两次反馈，第二次为总体评价原话）："工作台整体上……技术术语太多，而且描述方面不够详细，也没有任何背景，特别是需要让我了解做这个决策的上下文、原因，以及不同决策的利弊。" 实测中他曾在背景不足的决策块上被迫盲选（"我不清楚 AFX 是什么"）。

**要求**（这次不是轻量约定，做成一等公民）：
1. choice/verdict 块协议增加结构化可选字段并显式渲染分区：
   - `background`（背景：为什么会出现这个决策、现状是什么）
   - `why`（为什么需要人来定、为什么是现在）
   - options 每项增加 `pros: []` / `cons: []`（利弊各自渲染，替代把一切塞进 desc）
   - 已有 `recommendation` 旁边补 `recommendReason`（推荐理由）
2. 渲染：决策块内固定次序呈现「背景 → 为什么需要你 → 选项（含利弊）→ 推荐及理由」，缺失字段的区块不渲染（向后兼容）；
3. 作者侧 lint（present 时 warn 不阻断）：`needsDecision:true` 的块缺 `background` 或选项缺利弊时警告——把"让不了解细节的人也能判断"变成默认约束而不是作者自觉；
4. **大白话原则写进 authoring 文档**：面向决策者的文案禁用未解释的术语/缩写，首次出现必须一句话解释（本条与 P3 术语表合并处理）。

**验收**：用带完整字段的样例 content 渲染出四段式决策块；lint 对缺背景的决策块给出警告；schema 对旧内容向后兼容。

## P2 · 约定：受众分层（技术细节对非技术决策者折叠）

**现象**：yaml/配置类技术块让决策者直接看不懂（原话："感觉看不太懂这些信息"）。与上一条同根：默认受众应是"不了解实现的决策者"。

**建议方向**：块级可选 `audience: "decider"|"tech"`，`tech` 默认折叠进"技术细节"区；或最低成本——文档层约定"面向决策者的轮次，技术映射一律 `needsDecision:false` + 折叠"。

**验收**：存在一种被文档化的方式让技术块默认不占决策者注意力。

## P3 · 作者侧术语一致性提醒

**现象**：作者（AI）在会话里把"工单"写成"票"，用户当场纠正。

**建议方向**：最轻量——在 authoring 文档/模板注释里加术语表约定即可；如要工具化，present 时对 content 全文跑一个可配置词表 lint（warn 不阻断）。

**验收**：至少文档层有术语约定入口。
