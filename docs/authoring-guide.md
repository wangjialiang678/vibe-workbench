# Authoring 指南：怎么写一轮让人看得懂的内容

> 给**产出 content.json 的 AI**（也给人）。所有规则都来自真实病例，见 [feedback-examples-2026-07-13.md](feedback-examples-2026-07-13.md)。
> `workbench present` 会跑 [作者侧 lint](../src/protocol/lint.mjs) —— **warn 不阻断**，但每条 warn 都对应一次真实的失败。

## 0. 默认受众：不了解实现的决策者

创始人原话（2026-07-13 总体评价）：

> "工作台整体上……技术术语太多，而且描述方面不够详细，也没有任何背景，特别是需要让我了解做这个决策的**上下文、原因，以及不同决策的利弊**。"

**最隐蔽的危害**：没有背景的决策块**不是"没人答"，而是产出零质量的伪决策**——用户照样点了推荐项（病例 1），作者不敢采信，下一轮重问，白白浪费一轮往返。

## 1. 决策块四段式（硬要求）

`needsDecision: true` 的块必须给齐四段，渲染器按固定次序呈现：

```jsonc
{
  "type": "choice",
  "needsDecision": true,
  "background": "一句话本质类比 + 现状。这东西是谁做的、现在什么状态、为什么突然要处置它。",
  "why": "为什么需要人来定、为什么是现在。预先消解「是不是出错了」的焦虑。",
  "options": [
    { "id": "a", "label": "动词+名词（不要 Yes/No/确定/取消）",
      "pros": ["选了之后会发生什么好事"],
      "cons": ["代价 / 风险 / 不可逆之处"] }
  ],
  "recommendation": "a",
  "recommendReason": "为什么推荐它 + 四维自评（见下）"
}
```

**四维自评**（放 `recommendReason` 或 `why`，让用户一眼看出"这题为什么归我、错了多大事"）：
> 有无标准答案？ / 置信度？ / 重要性？ / **可回退性**（错了能不能反悔）

**选项要讲后果，不讲机制**：
- ✗ "两套自动修复并存会互相合并冲突；AFX 的存量 ai/** 分支归档"（讲机制）
- ✓ pros: ["不再有两套系统抢着改同一份代码"] · cons: ["AFX 的本地通道暂时用不了（代码还在，随时能重开）"]（讲后果 + 可回退）

## 2. 大白话原则：术语首次出现必须解释

**术语必须先回答"这是什么、跟我有什么关系、不办会怎样"，然后才轮到问题本身**（病例 3：用户直接回"没听懂"）。

- ✗ "Developer ID / 公证凭证的就绪时间表？"
- ✓ "**一句话：苹果的『软件签名证书』，没有它你的 App 发给别人会被 macOS 拦下。** ……**对我们的影响：不阻塞内测**，只影响将来公开分发。**给你的问题**：打算什么时候办？"

lint 规则 `unexplained-jargon` 会揪出正文里出现、但 `background`/`why` 里没解释的缩写。

### 术语表约定（P3）
- **同一概念全程同名**：作者曾把"工单"写成"票"，用户当场纠正。一轮之内、跨轮之间都不许换词。
- 项目专有名词在**首次出现处**用一句话解释；后续可直接用。
- 白名单（可直接用、无需解释）：AI / UI / UX / API / PRD / MVP / JSON / HTML / CSS / URL / CLI / IDE / PR / QA / FR / AC / NFR / ASR …（见 `lint.mjs` 的 `ACRONYM_ALLOW`，可扩充）

## 3. 一块一问

一个 `freetext` 里塞三个问题 → 用户被迫自行编号作答；"没听懂"这类元反馈失去针对性载体；跨轮 diff 也失效（块粒度错了）。**一个问题一个块。**（病例 4）

## 4. 确认场景别用 editable

行为数据（病例 5）：预填草稿的 `editable` 块用于"确认"时**连续两轮无人应答**；同一内容改成 `verdict` + 大白话后**当轮获得"赞成"**。

- 只需要"行 / 不行" → 用 **`verdict`**。
- 确实需要用户改写 → 才用 `editable`（渲染器已提供「✓ 保持原样即确认」一键零摩擦通路）。
- 反馈里 `type: 'confirm'` = **看了不改**；`unanswered` = **没看**。两者语义不同，别混。

## 5. 技术内容用 `audience: "tech"`

`needsDecision:false` **不等于"不占注意力"**——技术块出现在决策者视野里仍制造"我应该看懂"的压力（病例 2："感觉看不太懂这些信息"）。

给技术映射/配置/YAML 类块加 `"audience": "tech"` → 自动折叠进「🔧 技术细节（决策者可跳过）」。

## 6. 嵌真实系统必须标 `live: true`

**文案救不了 affordance**：标题里写了"（真实产物，就地操作）"，用户仍回"哦我搞错了，这个是给我看的样例"（病例 7）。

`embed` / `prototype(iframe)` 指向**真实运行系统**时加 `"live": true` → 渲染红框 + 「⚡ 实时系统 · 就地操作会真实生效」角标。**实时性感知必须靠视觉层，不靠文案。**

## 7. 被验证有效的写法（内容基准）

1. **"AI 做了什么（大白话）"段** —— 用日常语言讲清改了什么、影响多大、动没动别的东西。
2. **就绪度对比表** —— 维度 × 选项的 markdown 表格 + 一句"你的直觉成立"收束。
3. **"为什么停下来等你"段** —— "这是保守期的正常动作，不是出了问题。"
4. **四维自评段** —— 见 §1。

## 8. 会话级留言

渲染页常驻「💬 给 AI 留言」输入区，回传为 `feedback.sessionComment`。用户对整体、对工作台本身的话有地方说了——**别再让用户把全局反馈挂在不相干块的批注里**（病例 6）。

## lint 规则速查

| 规则 | 触发 | 病例 |
|---|---|---|
| `missing-background` | 决策块缺 `background` | 1 |
| `missing-why` | 决策块缺 `why` | 8 |
| `missing-proscons` | choice 决策的选项缺 `pros`/`cons` | 1 |
| `missing-recommend-reason` | 有 `recommendation` 无 `recommendReason` | — |
| `editable-for-confirm` | 确认场景用了 `editable` | 5 |
| `multi-question` | 一个 freetext 塞多问 | 4 |
| `unexplained-jargon` | 正文有术语但 background/why 里没解释 | 3 |
