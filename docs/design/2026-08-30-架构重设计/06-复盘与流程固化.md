## 一、漏网问题的根因：三重失明重叠

本轮漏了三样（journal 未实现、README 未更、skill 开关未写），根子是同一个：

**验收体系只有"回归门"（证明没改坏），没有"完整性门"（证明该有的都有了）。**

- 对拍/守卫/golden 全是回归门。**新增物的"缺失"对回归门是零差异**——没写 journal = 文件树没变 = 对拍通过。
- 唯一守"做没做完"的是每期手写的 `--require-file` 清单，而它是**凭记忆从设计文档挑的**（设计→派工的有损翻译），journal 恰好被挑漏。
- 三轮评审全部审"设计"，没有一轮审"实现 vs 设计"。

三重失明（回归门天生看不见 + require 清单挑漏 + 无实现对照审）恰好重叠 → 永久隐形，直到人问起。

## 二、修正后的流程认识

### 1. 几乎没有"每个项目都必须"的步骤，普适的是判断法

决定用不用某机制的是情境轴：改造 vs 新建（→对拍）、委托 vs 亲做（→验收契约/完整性门）、
有无部署间隙（→运行面验证）、爆炸半径×可逆性（→整套重流程 vs 直接做）、有无设计文档（→完整性门）。

### 2. 三类东西分开，权威来源不同

| 类 | 例 | 归置 |
|---|---|---|
| 工程不变量（硬） | 验而不信、门配失败模式、不可逆先存档、有间隙验运行面 | 全局质量底线 + 技能 |
| 创始人偏好 | Codex 做具体活、说人话、白底克制、不碰商务 | 全局 CLAUDE.md / 记忆 |
| 判断启发（软） | 何时评审、何时停、投入配爆炸半径 | 技能里写"怎么判断" |

### 3. 时机原则：门在守护物诞生时就位（shift-left）

本轮做对的时机：动刀前打 tag、安全止血先行、**安全网先于动刀**、评审先于实现。
做晚了的（即漏网根源）：完整性清单应在设计冻结时机械抽取（非凭记忆、非最后补）；
文档同步应在每期改动时触发（非批到最后）；客户命脉的运行面验证应是部署的一部分；
安全透镜有独立触发（碰鉴权/多租户/外部输入即触发），不该是评审副产品。

### 4. 评审要有停止规则

判据收紧为"只列不解决就会走错或测假的硬伤；可留到实现期的细节不算阻断"后一轮收敛。
否则完美主义评审无限循环。
