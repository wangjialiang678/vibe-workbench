## 一、这个产品是什么

Vibe Workbench：把 AI 的思考渲染成可交互网页（决策卡、原型、图表、逐条表态），
用户/客户在网页上点选、批注、改写，提交后落盘并唤醒 AI 续跑下一轮。
核心循环：`AI present 一轮 content → 人交互 → feedback 落盘 → AI 读 feedback 续跑 → 下一轮`。

三个部署形态：创始人本机（日常工作台）、东京服务器 ×2（客户评审门户 review.ai-opc.studio、
云工作台）。真实客户（思锐 TMS 项目）正经由门户做需求评审，**不能长时间停摆**。

## 四、踩过的坑（每条都真实发生过）

1. **巨石自然积累**：app.mjs 曾 2450 行 0 导出、handleRequest 曾 1192 行一个函数。
   架构没有强制边界，功能一多就长回去。事后靠"守卫测试"（如 app.css 禁止硬编码字号）拦住回潮。
2. **存储不变量可绕过**：85+ 处 `fs.` 散在 8 个文件；"round 不许覆盖"只在 workspace.mjs
   一条路径生效，别处直接写盘就绕过。真实发生过门户内容被覆盖的事故（2026-08-19）。
3. **假测试**：曾有测试拿源码字符串做正则断言（"源码里有这行字"≠"行为对"）。
4. **e2e 盲区**：618 条测试全绿，仍漏掉「近似路径被前缀路由吞掉导致连接永久挂死」。
   最终抓住它的是**双服务器对拍**（新旧版同数据跑 42 条请求逐行 diff）——纯重构最有效的验收法。
5. **运行面间隙**：server 常驻不热载、浏览器三层缓存（已用 ?v= 资产版本击穿）、
   三份部署靠 rsync 手动同步，漂移风险常在（曾发生"仓库已修、线上未证实"）。
6. **执行代理会交付空壳**：重构派工曾收到"26 个路由 handler 全是转发、原函数改名后比原来还多一行"
   的假拆分，自述漂亮。验收必须点交付物数字，不能读总结。
7. **客户数据与代码同目录**：workspace/ 含客户真实评审内容，靠 gitignore 挡着；样张快照差点入库。
8. **mermaid 渲染竞态**：隐藏 tab 的零尺寸容器渲染崩溃、vendor 加载竞态，修过两轮。
9. **权限模型有机生长**：owner token + 参与者 token + 自报身份三层叠加；
   "无 token 返回 403 而非 404"这类语义靠隐式代码顺序保证，拆分时极易破坏。
10. **可用性兜底救过场**：feedback 永远落盘为 `workspace/<session>/round-N/feedback.json`，
    任何环节卡死都能直接读文件接管——**文件即事实源**是实战验证过的优点，别丢。

## 五、创始人的价值观约束（长期有效）

- 白底黑字、克制、专业的视觉（theme.css 令牌层已固化，重设计必须保留这套视觉成果）
- 不过度设计（YAGNI）；但也不头痛医头——要真边界，不要装饰性分层
- **一切可验证可测试**；关键路径打日志；冷启动测试（新会话只凭落盘物能否接管）
- 编码执行交给 Codex（tcd 派发 + 验收契约），架构与验收由主会话把关
- 目前零运行时依赖（package.json 无 dependencies）、前端无构建直接 ESM ——
  这是**现状**而非圣旨，是否保留属于本次要回答的问题

## 六、请你回答的问题（Q1–Q8）

  依赖方向如何强制（不能再靠自觉）？

  stream（6 会话 19 条）各自去留？砍错的代价是什么？
- **Q5** 迁移策略：绿地重写 + 数据迁移，还是绞杀式逐层替换？对拍 harness 如何作为全程安全网？
