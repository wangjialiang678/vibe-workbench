# 反馈病例集：真实文案样本与用户反应（2026-07-13，user-vibeloop 四轮会话）

**用途**：给本项目智能体的具体例子，配合 `docs/iteration-brief-2026-07-13.md` 使用。每个案例含：当轮呈现的**文案原文**（从 content.json 摘录）、用户的**反应原话**（从 feedback.json 摘录）、问题拆解、以及（如有）后续轮次修正后用户接受的**对照版本**。设计 `background`/`pros`/`cons` 等新字段和作者 lint 时，建议直接拿这些真实文本当 fixture 与验收样例。

**完整语料**：私有归档（`workspace/` 目录不随仓库分发），本文是从中抽出的典型病例。背景：该会话用于 user-vibeloop 项目（AI 反馈闭环框架）的决策确认，决策者是创始人 Michael（产品视角，不看代码）。

> 脱敏说明：引语中的内部人名与仓库/系统名已替换为等价假名（AFX、旧产品仓、同事等），其余文本为原始记录，病例的教学意义不受影响。

## 案例 1 ·【最典型】AFX 决策块：术语墙 + 零背景 → 用户"盲选"

**R1 呈现原文**（块 `b-ime-afx`，choice，needsDecision）：

> 标题：AFX 处置：旧产品仓 main 里已有前代三通道 AI 自动修复，与 vibeloop 同问题域会撞车
> 选项 1「停用 AFX，vibeloop 全面接管（推荐）」desc：两套自动修复并存会互相合并冲突；AFX 的存量 ai/** 分支归档
> 选项 2「共存观察一段时间」desc：AFX 继续跑本地通道，vibeloop 只处理用户反馈；需人工保证不碰同一问题
> 选项 3「接入时再议」desc：视频剪辑先行的话，这个决策可以推迟

**用户反应**（R1 feedback，选了推荐项 disable，但附评论）：

> "我不清楚 AFX 是什么，以及到底要解决什么问题。这也是给 vibe code 工作台的反馈：每个决议需要更多上下文和背景信息。"

**问题拆解**：
1. 缩写 `AFX` 全程未解释（它是该仓库里前人做的一套 AI 自动修 bug 系统，用户自己都不知道这个名字）；
2. "三通道""main""同问题域""撞车""ai/** 分支"全是行话；
3. 没交代背景：这东西是谁做的、现在什么状态、为什么突然要处置它；
4. 选项 desc 讲机制不讲**后果**（选了之后会发生什么、错了能不能反悔）；
5. 最隐蔽的危害：用户**照样完成了提交**（选了推荐项）——没有背景的决策块不是"没人答"，而是产出**零质量的伪决策**。作者侧因此没敢采信，下一轮重新问，浪费一轮往返。

**R2 修正版原文**（块 `b-afx-explain`，用户看懂后在重问块上确认了同一选择）：

> **一句话：旧产品仓库里已经住着一个"老版的 vibeloop"。**
> 它叫 AFX，是同事早前在个人分支上做的"AI 自动修 bug"系统（就是我们调研过、借鉴过凭证剥离设计的那个雏形），上个月已经并入 main。它会：自己开分支 → AI 改代码 → 提 PR 等人批准。
> **要解决的问题：一个仓库不能住两个自动修理工。** 如果 AFX 和 vibeloop 同时运行，两个系统会各自开分支改同一份代码——互相制造合并冲突、重复修同一个 bug、你要看两套等待批准的队列。
> **"停用"意味着什么：不删任何代码**，只是不再触发 AFX……
> **四维评估**：无标准答案？——有，共存客观上会冲突，这是技术判断；置信度——高；重要性——中（只影响输入法接入时点）；可回退性——完全可回退（AFX 代码还在，随时能重新启用）。

**可复用模式**（P1 结构化字段的内容原型）：一句话本质类比（background）→ 要解决的问题（why）→ 每个选项"意味着什么/后果/可回退性"（pros/cons）→ 推荐理由与 AI 自评（recommendReason）。

## 案例 2 · 技术配置块："感觉看不太懂这些信息"

**R2 呈现原文**（块 `b-video-verify`，markdown，needsDecision:false，标题已声明"无需逐行确认"）：

> 标题：verify 与风险分级草案（技术映射，无需逐行确认，异议直接批注）
> ```yaml
> verify:
>   - name: unit                       # 现成：85 个离线测试，1 秒全绿
>     run: python3 scripts/run_tests.py
>   - name: export-integration        # 待补：小样本 ffmpeg 导出 → ffprobe 断言时长/流规格/字幕时间戳
> …
> riskTiers:
>   high: ["prompts/**", "docs/specs/**", …]
> gates: { low: auto, medium: human, high: human }   # 第一周 medium 也人审…
> ```
> 为什么 high 里有 `prompts/**` 和 `asr_runner.py`：改提示词等于改产品意图……

**用户反应**（R2 feedback）：

> "感觉看不太懂这些信息。"

**问题拆解**：
1. 即便标了"无需确认"，技术块出现在决策者视野里仍制造"我应该看懂"的压力——`needsDecision:false` 不等于"不占注意力"；
2. 术语密度：verify / riskTiers / glob / gates / 硬门槛 / 软信号 / 评分棘轮，每个都需要前置知识；
3. 对产品的启示：需要**受众层**的机制（`audience: tech` 默认折叠），而不能只靠作者把每个块都翻译一遍。

**R3 对照**（同类信息大白话化后，用户立即表态）：块 `b-video-constraints-ok`（verdict）——这五条在 R2 是 editable 技术清单被跳过，R3 翻译后**当轮获得"赞成"**：

> 五条红线（大白话版）：**①不装任何 Python 包**（保持项目零依赖的架构卖点）；**②测试永远离线**（不许把要花钱、要联网的真实 ASR/大模型调用混进测试）；**③你的视频和转写内容不出本机**（现有 ASR 上传链路除外）；**④老项目文件永远打得开**（本地数据格式向后兼容）；**⑤已有接口行为不变**（依赖它的东西不会悄悄坏）。
> AI 修复违反任何一条会被评审官直接驳回。已按"初稿"生效……点赞成即转正，有异议写批注我立刻改。

## 案例 3 · 专有名词直接入题："没听懂"

**R1 呈现原文**（块 `b-ime-open`，freetext 内第②问）：

> ② Developer ID / 公证凭证的就绪时间表？（决定发布门何时能真正走通，不阻塞接入）

**用户反应**：

> "2. 没听懂"

**R2 修正版原文**（块 `b-devid-explain`，用户随即给出决策"这个晚一点办，但不影响内测。"）：

> **一句话：苹果的"软件签名证书"，没有它你的 App 发给别人会被 macOS 拦下。**
> 细节：加入 Apple Developer Program（99 美元/年）后可以拿到 Developer ID 证书，用它给 App 签名+公证（notarization），别人下载后才能正常双击打开；否则 macOS 会弹"无法验证开发者"，用户要去设置里手动放行——内测用户会被吓跑。
> **对 vibeloop 的影响**：……**不阻塞接入**……只影响将来公开分发。
> **给你的问题**：打算什么时候办证书？

**模式**：专有名词必须先回答"这是什么、跟我有什么关系、不办会怎样"，然后才轮到问题本身。

## 案例 4 · 一个 freetext 塞三个问题

**R1 呈现原文**（块 `b-ime-open`）：

> 三个开放事实问题（知道多少答多少）
> ① 延迟指标要不要写死进 metrics（现状是描述性的"端到端约 1-2 秒"，无 p95 SLO）？
> ② Developer ID / 公证凭证的就绪时间表？……
> ③ 合并推 origin（组织仓）还是 personal 远端（个人仓）？

**用户反应**（被迫自行编号作答）：

> "1.不要写死
> 2. 没听懂
> 3. origin ，是我们的组织仓库"

**问题拆解**：三问合一导致——回答与问题的对应关系靠用户手工维护；"没听懂"这类元反馈失去针对性载体（没法就地追问第 2 问）；后续轮次的 diff/复用（同 block id 跨轮）也失效，因为块粒度错了。**建议：一块一问**；或 freetext 支持子问题结构。①里的 "p95 SLO" 同时踩了案例 3 的坑。

## 案例 5 · 行为数据：确认类内容用 editable 是高摩擦（连续两轮未答）

**现象时间线**（unanswered 字段是工作台自己报的）：
- R2 呈现三个 editable 草稿块（`b-video-constraints` / `b-ime-goal` / `b-ime-constraints`，预填全文，标题写"改或确认"）→ **R2 unanswered 恰好是这三个**；
- R3 再次呈现：`b-video-constraints` 改成 verdict（大白话五条红线）→ 当轮"赞成"；`b-ime-goal`/`b-ime-constraints` 仍是 editable → 用户**没有编辑**，而是各写了一条 comment："同意"。

**拆解**：editable 的默认动作语义是"改写"，对只想说"行"的用户是高成本操作（要通读全文、要决定动不动、动了还要为改动负责）；用户最终用批注"同意"绕过了控件本身。**产品建议**：确认场景用 verdict/一键；editable 增加显式"保持原样即确认"按钮；`unanswered` 语义区分"没看"与"看了不改"。

## 案例 6 · 重要反馈寄生在不相干块下（常驻留言缺口的实锤）

**R2 场景**：块 `b-macstudio-note` 是一个纯状态说明块（"Mac Studio：等你开机……开机后在任何地方跟我说一声"）。用户在**这个块**的批注里写下的却是给工作台的产品级反馈：

> "工作台如何告诉你？是不是工作台还缺少一个常驻的让用户给 AI 反馈的入口？这是给工作台的反馈，你也记录一下。晚一点所有 vibe code 工作台的反馈，可以总结成一个文档给那个项目"

**拆解**：块级批注是用户唯一的自由发言通道，任何全局性、跨块、给系统本身的话都被迫寄生在某个碰巧打开的块下。对应简报 P1"会话级常驻留言入口"。

## 案例 7 · 文案救不了 affordance："真实产物"写在标题里仍被当样例

**R4 呈现原文**（embed 块）：

> 标题：vibeloop 决策队列（**真实产物，就地操作**）
> 且前置 markdown 块通篇是操作指引："**你要做的**：在下面嵌入的决策页里点「批准合并」。口令在终端里取：…"

**用户反应**（隔轮聊天原话）：

> "哦我搞错了，这个是给我看的样例"

**拆解**：括号里明明白白写了"真实产物，就地操作"，用户仍按样例理解——**证明这不是文案问题，是视觉 affordance 问题**：嵌入内容与工作台自身的演示性内容长得一模一样。这条给简报 P1"live 角标"提供依据，同时划清边界：术语/背景类问题靠文案规范能解决，"实时性"感知必须靠视觉层（角标/边框/呼吸点）。

## 案例 8 · 反例合集：被验证有效的写法（新字段的内容基准）

以下写法在实测中直接换来了顺畅决策，可作为 `background`/`pros`/`cons`/`recommendReason` 渲染样式的内容基准：

1. **"AI 做了什么（大白话）"段**（R4 `b-r4-approve`，随后用户完成两次真实批准）：
   > 给视频剪辑项目新增了一条"导出链路体检"测试——用 ffmpeg 凭空合成一段 10 秒测试视频（不依赖任何真实素材），跑一遍完整导出，然后核对三件事：成片时长和剪辑计划一致（误差 ±200 毫秒内）、画面和声音轨都在、字幕时间码顺序正确且不越界。……**只新增了一个测试文件，没碰任何现有代码**，全套测试从 85 条变 86 条、全绿。
2. **就绪度对比表**（R1 `b-order-analysis`，两项目逐维对比 + 摩擦估计，用户顺利选定 video-first）：结构 = 维度 × 选项的 markdown 表格 + 一句"你的直觉成立"收束。
3. **"为什么停下来等你"段**（R4）：
   > 宣言里定了第一周所有中风险改动都人审。这是保守期的正常动作，不是出了问题。
   ——预先消解"是不是出错了"的焦虑，属于 `why` 字段的标准内容。
4. **四维自评段**（案例 1 的 R2 修正版末段）：有无标准答案 / 置信度 / 重要性 / 可回退性——让用户一眼看出"这题为什么需要我、错了多大事"。
